# Platform Fees

## Current rule

The backend config in `src/lib/platform-fees.js` uses a fixed BRL fee of 30 integer cents for every confirmed paid sale. It is not percentage-based and tenants cannot change it. `pix_direto` is the only exempt gateway and records a zero-cent `WAIVED` audit entry.

Fees are created only by `deliverPaidOrder`, after a conditional order transition to `paid`, in the same Prisma transaction as access creation. A unique ledger key combines workspace, normalized gateway, provider transaction ID, and entry type. Database uniqueness plus `createMany({ skipDuplicates: true })` makes repeated callbacks idempotent.

The fee ledger is separate from payment credentials. It stores integer cents, tenant/workspace, order, gateway, provider transaction/reference, type, timestamps, status, and metadata. Unsupported automatic collection remains `PENDING`; that status does not mean money was received. Only a provider-confirmed 30-cent split can move a fee to `RECEIVED`. Refunds retain the original entry and add a negative `REFUND_ADJUSTMENT`.

Each ledger entry also has immutable `PlatformFeeEvent` rows for fee generation/waiver, split receipt, and refund transitions. The current ledger row is a convenient snapshot; the event rows preserve the sequence of status changes.

## Gateway support

| Gateway | Checkout status | Fee rule | Automatic split/collection |
| --- | --- | --- | --- |
| Mercado Pago | PIX checkout connected | 30 cents per approved order | Official Marketplace 1:1 uses seller OAuth and `application_fee: 0.30`; fee is marked received only if the payment lookup confirms the exact application fee. |
| AmploPay | PIX checkout connected | 30 cents on confirmed order | No fixed split was verified in the provider material available to this implementation; ledger stays pending. Callback uses the per-order HMAC query signature currently generated by the app. |
| SyncPay | PIX cash-in connected | 30 cents on API-confirmed paid order | Cash-in/webhook and transaction lookup are documented. No fixed split was confirmed for the cash-in endpoint; ledger stays pending. Notifications are verified by querying the tenant's authenticated transaction API. |
| PIX Direto | PIX generation and manual review | Exempt, zero cents | No fee ledger obligation and no split. A zero-cent `WAIVED` row is retained for audit. |
| Pushin Pay, Átomo Pay, Nexus Wallet, Stripe, Oasy Pay | Not connected to checkout | No sales/fees until implemented | No split is claimed. |

The SyncPay public docs mention subscription plans but this application currently creates one-off PIX cash-ins. Product interval fields are metadata only; automatic renewal is not enabled. If future provider subscription invoices are represented as distinct paid orders with unique provider transaction IDs, each order will pass through the same fee service. PIX Direto remains exempt.

## Mercado Pago Marketplace setup

1. The platform administrator saves its Marketplace `APP_ID`/Client ID and Secret Key/Client Secret under **Administração → Financeiro → Conta de recebimento da plataforma**. An optional webhook signing secret may also be saved.
2. Register the displayed Redirect URI in the Mercado Pago Marketplace application.
3. Each tenant authorizes the Marketplace connection from **Integrações**. OAuth state is random, stored as a hash, tenant-bound, expires after ten minutes, and can be consumed once.
4. Seller access/refresh tokens are encrypted at rest. The server refreshes expired access tokens with the platform application's credentials.

Marketplace support must be enabled for the platform application and seller accounts by Mercado Pago. Credentials saved in the admin panel alone do not prove that the Marketplace split is enabled.

## Security and tenant boundaries

- Tenant gateway credentials stay in the existing encrypted integration storage. Platform receiving credentials are stored separately in `PlatformReceivingAccount` and are accessible only to the configured admin email.
- The admin ledger API is restricted to the existing `isAdminEmail` authorization. The customer summary resolves workspace IDs from the authenticated user and never accepts tenant IDs from the browser.
- Webhook handlers use provider signatures where configured and confirm final statuses against provider APIs before changing the order to paid. Never mark a ledger row received based on a browser request or an unverified webhook body.
- No secrets are returned to client components or written to logs.

## Finance pages

- **Administração → Financeiro** shows paid sales, generated/pending/received/failed fee totals, exempt sales, filters, ledger references, and the platform receiving account state.
- The tenant dashboard shows fee totals scoped to its own workspaces. `PENDING` is explicitly distinct from `RECEIVED`.

## Add a gateway

1. Integrate the provider API in the existing payment factory and register the provider in the central catalog/options.
2. Ensure each successful provider payment has a distinct `Order.paymentId` and the webhook handler verifies the provider's official status before calling `deliverPaidOrder`.
3. Do not add fee logic to the gateway or frontend. The shared `PlatformFeeService` defaults to 30 cents; add an exemption only to `FEE_EXEMPT_GATEWAYS` with an explicit business approval.
4. Implement real split only from current provider docs. Otherwise keep the ledger pending and never label it received.
5. Add tests for paid, pending, cancelled, expired, duplicate, refund, tenant isolation, and integer-cent calculations.

## Validation

Run `npm test`, `npm run lint`, and `npm run build`. Current focused tests cover integer cents, PIX Direct waiver, non-paid states, repeated webhook delivery, fee status, OAuth state handling, Marketplace payload/signature verification, and refund adjustments.
